# Fresh source-syntax controls before frontend consolidation

Status: protocol registered before collecting fresh model replies. No new syntax is promoted.
This is a control pilot, not evidence of universal superiority or a completed unification.

## Question and subjects

Compare the existing Canonical and Dense source views on the same application maintenance tasks,
using the current parser/edit implementations and the sealed 14-task compiler frontend application
set in `tools/app-edit-tasks.ts`. Retain its seal, starters, acceptance tests and wrong/reference
edits. Neither task answers nor hidden tests are supplied to subjects. The historical TypeScript
control remains available; it is not a replacement for the Canonical-versus-Dense comparison.

The new `--surface=canonical|dense` option belongs only to the benchmark. It does not introduce a
compiler dialect. There is no `unified` benchmark cell until an actual unified frontend exists.
Canonical remains the default and uses `MODEL_GUIDE.min.txt`; Dense uses `MODEL_GUIDE.dense.txt`.
Both use the same structured edit protocol, dependency function views and program-signature scope.
Prompt preparation and scoring execute TypeScript source directly with Bun on a clean committed
checkout. Prompt dumps have a `.manifest.json` sidecar binding their bytes, guide, starters, task
seal, program-view scope and complete implementation Git commit/tree. Scoring verifies that the
implementation did not change during the run. Node imports remain usable by existing test tools;
compiled CLI measurement execution is refused rather than silently trusting stale `dist` files.
All guide and task-set hashes, source surface, model identifier and harness self-check result must
be retained. Primer costs count toward total cost; different primers are not free setup.

## Harness checks

For both surfaces, reference edits must pass, starters must fail, and wrong-but-plausible edits
must apply and fail the same sealed acceptance tests. Dense self-check replies are generated by
applying the existing Canonical references through `EditSession`, selecting the changed functions
by revision, and formatting them with `formatDense`; no Dense reference solution is hand-written.
These generated references are harness controls only, never subject replies or model outcomes.

## First pilot

Use one fresh independent subject per task and surface: 28 first attempts, at most one repair per
attempt, for at most 56 model calls. Subject creation requires the authorization applicable to the
execution environment; do not substitute this agent's answers or reference edits. Use the same
reported model and settings in both arms. Alternate pair order by the low bit of the first byte of
SHA-256(task ID). Keep arms independent and preserve the complete prompt/reply transcript.

A repair receives only the original prompt, its own first reply and the harness's bounded rejection
message, following the existing rollback protocol. No outcome-dependent prompt or primer changes,
extra retries, selected successes, or cross-arm conversation history are permitted.

For an installed Codex subject, use an isolated fresh session with no project history or repository
instructions. Supply only the dumped prompt and collect the subject's final response. Record tool
activity; a subject that reads the repository, answers or hidden tests contaminates the trial and
must be reported as invalid, with its consumed usage retained. Do not silently replace it.
No provider API credentials are currently configured. Logged-in CLI availability alone is not
permission to spawn independent subjects when the session instructions require explicit approval.

## Accounting and decision

Report first-attempt and after-repair accepted counts, invalid trials, failures, repairs, input/output
usage, tokenizer counts, and total tokens per accepted edit. Include failed-attempt and repair costs.
Keep locally counted primer/view/reply tokens distinct from provider-reported usage. Unknown
reasoning usage and caching are null, never assumed zero. Preserve actual provider usage including
fixed runner/system overhead where available. Report intervals and per-task pairs; do not hide an
accuracy loss behind a source-token average. No timing claim is made from a loaded machine.

This small single-application pilot can expose regressions and guide the next candidate. It cannot
prove noninferiority across all applications, providers, targets or edit protocols. Before replacing
the official source frontend, add independent application cases, compare the implemented unified
candidate against both retained controls, and verify source migration, self-hosting, target behavior,
compilation cost, memory and emitted artifacts. A source-only token saving never overrides a
measured acceptance loss. Historical results stay historical.

## Commands

```sh
bun tools/app-edit-bench.ts self-check controls-canonical.json
bun tools/app-edit-bench.ts self-check controls-dense.json --surface=dense
bun tools/app-edit-bench.ts dump prompts-canonical.json a0
bun tools/app-edit-bench.ts dump prompts-dense.json a0 --surface=dense
bun tools/ai-edit-subjects.ts prompts prompts-canonical.json subjects-canonical
bun tools/ai-edit-subjects.ts prompts prompts-dense.json subjects-dense
# Collect independently produced replies with the existing subjects helper, then score:
bun tools/app-edit-bench.ts run replies-canonical.json report-canonical.json a0 MODEL
bun tools/app-edit-bench.ts run replies-dense.json report-dense.json a0 MODEL --surface=dense
```

Keep scratch output in the task's repository scratch directory. Published reports must use
`tools/scrub-results.ts`. Do not label prompt preparation or a passing reference self-check as
measured AI success.
